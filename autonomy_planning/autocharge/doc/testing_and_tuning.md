# 测试与调优建议

本文档给出当前自动回充策略的推荐验证方法。重点不是只看单条日志，而是按固定区域反复验证收敛性。

## 1. 推荐测试目标

验证应覆盖以下四类起点：

| 测试区 | 典型初始现象 | 目标 |
| --- | --- | --- |
| 远区 | 初始看不到红外 | 能稳定进入单侧区或中心区 |
| 左偏区 | 先看到左侧单边红外 | 能进入 `BIAS_LEFT` 并最终收敛到 `CENTER` |
| 右偏区 | 先看到右侧单边红外 | 能进入 `BIAS_RIGHT` 并最终收敛到 `CENTER` |
| 近中心区 | 初始就能看到中心相关信号 | 能尽快进入 `CENTER` 并触发 `charge_connected` |

## 2. 推荐验证流程

### 2.1 单次人工验证

推荐顺序：

1. 启动仿真与控制节点。
2. 把机器人放到指定测试区域。
3. 发布 `/dock/start`。
4. 观察 `/dock/state`、`/ir/dock` 和日志中的 `dist`。

重点看三类结果：

1. 是否正确进入对应区域状态。  
   例如右侧单边观测应进入 `BIAS_RIGHT`。

2. 是否避免无意义震荡。  
   例如不应在很短时间内反复 `BIAS_LEFT <-> BIAS_RIGHT`。

3. 是否最终触发 `charge_connected`。  
   `SUCCESS` 必须来自接触成功，而不是纯几何距离。

### 2.2 批量测试

建议使用 `docking_tester` 做多轮随机验证，特别适合检验边界区是否稳定：

```bash
ros2 launch autocharge autocharge.tester.launch.py \
  max_tests:=50 \
  case_timeout_s:=50.0 \
  random_pose_y_min:=-0.08 \
  random_pose_y_max:=0.08 \
  random_pose_yaw_min:=-0.15 \
  random_pose_yaw_max:=0.15
```

这类测试要重点回答两个问题：

1. 成功率是否稳定提升。
2. 是否出现“更少成功但更快失败”的伪优化。

## 3. 推荐日志判据

以下日志现象说明策略在收敛：

### 3.1 远区

- `SEARCH` 阶段 `dist` 没有异常大幅波动；
- 首次捕获红外后，能稳定进入 `BIAS_LEFT` 或 `BIAS_RIGHT`；
- 不会长时间停留在纯 `SEARCH` 且一直没有新的红外证据。

### 3.2 左右偏区

- `SEARCH` 整圈后（或确认中心后）进入对应 `BIAS_*`，而不是首次见侧边就锁边；
- `BIAS_*` 保持红外可见：有信号慢速前进，丢信号停转回找（闭环 `TRACK`，非开环扫角）；
- 状态不会在极短时间内来回切边；
- 整体上 `dist` 应该逐步下降。

### 3.3 中心区

- 进入 `CENTER` 后不会因为短暂无信号立刻退回 `SEARCH`；
- 丢失 `0x04` 时应 `vx≈0` 并 yaw 回找，而不是盲目前进；
- 接近接触时角速度应总体变小。

### 3.4 成功区

- 出现 `charge_connected`；
- 状态进入 `SUCCESS`；
- 命令速度归零。

## 4. 常见失败模式

### 4.1 左右来回抖动

表现：

- `BIAS_LEFT -> BIAS_RIGHT -> BIAS_LEFT` 高频切换；
- `dist` 长时间卡住不降；
- 红外观测在单边区边界反复闪烁。

说明：

- 当前策略对边界区过于敏感；
- bias 周期未完整执行；
- 过早响应瞬时 opposite-side 证据。

### 4.2 过早离开 CENTER

表现：

- 已经接近中心区，但由于短暂无信号又回到 `SEARCH`；
- 最后几厘米阶段反复重找红外。

说明：

- 对中心束边界容忍度不够；
- 丢 `0x04` 后未停前进并用 side hint 回找，或超时过短导致过早退 `SEARCH`。

### 4.3 近场接触失败

表现：

- 看起来几何上已接近，但始终没有 `charge_connected`；
- `CENTER` 内前进和微调互相打架；
- 或 `CENTER` 下长时间 `ir=(0x00,0x00)` 仍 `vx>0`（盲冲）。

说明：

- 进入接触区后仍然修正过度；
- 丢中心束后仍盲目前进，横向误差被放大；
- 最后阶段没有足够稳定地对准中心发射器。

## 5. 推荐调优顺序

为了保证易维护，调优顺序建议固定如下：

1. 先看布局与策略是否一致。  
   如果实际行为和 `docking_strategy.md` 不一致，优先改状态机逻辑。

2. 再看状态切换是否稳定。  
   例如 `SEARCH -> BIAS_* -> CENTER` 是否符合预期。

3. 最后再调已有参数。  
   只在必要时调整 `config/sim.yaml` 与 `config/docking.yaml` 中已经存在的参数，不优先新增参数。

## 6. 不建议的调优方式

以下方式会让系统越来越难维护：

1. 为每个异常现象单独新增一个参数。
2. 只针对某一条日志做局部修补，而不看整体状态流。
3. 让成功条件同时依赖多种互相冲突的标准。
4. 用更大角速度或更大前进速度“硬冲”中心区。

## 7. 推荐的成功标准

一轮优化是否有效，建议至少满足以下三条中的两条：

1. 批量成功率提升。
2. 左右边界区的状态抖动明显减少。
3. `CENTER` 阶段的平均持续时间缩短，但最终 `charge_connected` 率不下降。

仿真/批量测试中：**成功**仅当 `charge_connected` 后进入 `SUCCESS`；**失败**包括 `ABORT`（含接触点越过桩面且未接通，`fail_on_dock_overrun_enable`）与超时。
